# 示例会诊（脱敏重构）

> ⚠️ 本文件是**依据真实会话脱敏重构**的示例，用来展示输入输出的形态与
> "独有观点 / 矛盾点"两栏的价值。不是逐字记录，成员名称与结论均已泛化。

## 1. 触发

```
用户：帮我找个第二意见 —— 本地大模型服务的 KV 缓存池，
      设成"够用就行"还是"开到模型窗口上限"？我担心开大了会变慢。
```

## 2. 阵容探测

先跑探测脚本（避免以为在线、其实全超时）：

```
成员          类型            端点                        状态    备注
宿主模型      当前会话        (本进程)                    在线    永远在场，担任裁判
CLI agent     云端免费模型    <OPENCODE_CLI>              在线    可执行文件存在
本地端点 1    OpenAI 兼容     http://127.0.0.1:1920/v1    在线    health 200
本地端点 2    OpenAI 兼容     http://127.0.0.1:1919/v1    离线    端口未监听（服务未启动？）
```

→ 实际阵容：**3 票**（CLI agent + 本地小模型 + 宿主模型），本地大模型缺席并如实报告。

## 3. 并行发起

三个成员同时后台跑，问题以统一模板下发（要求独立作答、给置信度）。
CLI agent 超时 180s，本地端点 300s。

## 4. 汇总输出

```markdown
## 会诊结果
| 成员 | 结论一句话 | 状态 |
|---|---|---|
| CLI agent | 开到上限，多出的 KV 不会拖慢生成，只是少了并发余量 | ✅ 已作答 |
| 本地小模型 | 保守设置更稳，缓存开大可能引发内存不足 | ✅ 已作答 |
| 宿主模型（裁判） | 取决于架构：若为混合状态层架构，KV 每 token 开销很小，可开到上限 | ✅ 已作答 |
| 本地大模型 | —— | ⚠️ 缺席（端口未监听） |

### 🤝 共识（多数成员一致）
- KV 池扩大本身不会线性拖慢单次生成；瓶颈通常在权重搬运带宽，而不是 KV。
- 唯一代价是显存占用与并发余量。

### 🔵 独有观点（仅一家提出 — 最有价值的部分）
- **宿主模型**：对"混合 Mamba/GDN 架构"这类模型，大部分层不持有逐 token 的 KV，
  因此 KV 扩容的显存代价远低于同等规模的纯注意力模型 —— 这解释了为什么实测中
  KV 翻两番而显存几乎不变。可信度：**高**（可被实测验证：扩容后记录显存与速度）。
- **本地小模型**：提出"缓存开大可能 OOM"的风险。可信度：**中**（结论方向对，
  但未区分架构；对纯注意力模型成立，对混合架构不成立）。

### ⚠️ 矛盾点（成员互不相同）
- 小模型说"开大更慢/更危险"，CLI agent 与裁判说"开大不拖慢"。
  **裁判意见**：错在把"KV 容量"与"注意力计算量"混为一谈。KV 容量影响的是
  显存与并发，不直接增加每 token 的计算量；而小模型大概率把"更大的窗口"
  与"更长的上下文"混在一起了 —— 上下文变长才会变慢。
- **额外提醒**：本地小模型与裁判出自不同基座，但两个本地端点若同源，
  它们的一致意见不能算独立验证。

### 🏁 裁判总结
1. 先确认架构类型（纯注意力 vs 混合状态层），再决定 KV 策略。
2. 混合架构：可以把 KV 池开到模型窗口上限，代价几乎只有显存；
   实测应记录 3 个数字：可用上下文上限、冷/热生成速度、显存占用。
3. 纯注意力架构：KV 扩容会实打实吃显存，需在"上下文"与"并发"之间取舍。
4. 无论哪种，**用一次对照实验代替争论**（同一脚本、同一提示词、只改一个参数）。
```

## 5. 这次会诊真正值钱的地方

不是"三个模型都回答了"，而是：

1. **独有观点栏**给出了一条别人没说、但可验证的机制解释（架构决定 KV 开销）。
2. **矛盾点栏**把"看似对立的两个结论"还原成"一个概念混淆"，而不是简单投票。
3. **缺席如实报告**：用户知道这次只有 3 票，不会误以为有 4 个独立来源。
4. **裁判给出了可执行的下一步**（做一次对照实验），而不是停在结论上。

## 6. 反例：什么时候不该开面板

```
用户：Python 里 list.append 的复杂度是多少？
```

并可能引入一个自信的错误答案（见 README「已知局限」）。
